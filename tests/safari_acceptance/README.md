# Safari and Mobile Safari long-session acceptance

The adoption acceptance design (`tests/adoption_acceptance/`) run against real
Safari, Mobile Safari in an iOS Simulator, and Playwright WebKit for
comparison, on GitHub-hosted macOS (`.github/workflows/safari-acceptance.yml`).

## What runs

Per engine, one virtual machine: build the packaged default site on the runner
from the reviewed runtime archive (`terrio_release_assets.py acquire`) and the
exact inputs of the accepted Windows adoption run (`inputs.json`: two pilot
streams already public on gh-pages, the depth stream and two synthetic fixtures
as draft-release assets; every byte verified). Check the site against the seven
independently frozen `candidate-pins.json` (committed sources and the locked
Terrio assets; a test keeps them in step). Then the unchanged driver design:
independent h5wasm-vs-Terrio decoder preflight, 3 fresh-context trials x
(cold + warm first render, 80 stream switches with three slider renders each,
20 each of fetch-cancel / preparation-cancel / malformed recovery) per decoder,
with exact numeric and RGBA verification, worker/module reuse checks and a
working-set sample after every switch.

```sh
ENGINES=safari node tests/safari_acceptance/run.mjs NEW_DIR      # or ios-simulator, webkit
node tests/safari_acceptance/evaluate.mjs NEW_DIR/raw.json safari
```

## How Safari is driven

`tests/adoption_acceptance/safari.mjs` implements exactly the Playwright
surface the driver uses over Apple's `safaridriver` (W3C WebDriver):
`goto`, `evaluate`, `waitForFunction` (in-page polling), `locator`,
`addScriptTag`; a context is one WebDriver session. Timings are unchanged: they
are in-page `performance.now()` stamps from the same instrumentation.
WebDriver has no init-script, console or network hooks, so the acceptance
server injects the Worker counter and an error capture into served HTML (only
during a Safari session) and records every >= 400 or abandoned response
itself. Engine-internal console messages the page cannot see are therefore not
captured -- a known limitation.

Mobile Safari: `safari:useSimulator` with the booted iPhone simulator's UDID;
Remote Automation is enabled through the simulator's Safari defaults. iOS has
no window sizing; the simulator's own viewport is used.

## Working set on macOS

`tests/adoption_acceptance/processes.mjs`. WebKit's WebContent, Networking and
GPU processes are launchd XPC services, not descendants of the browser, so they
are attributed by executable path: Safari = everything under `Safari.app` plus
the system WebKit XPC services; Mobile Safari = `MobileSafari.app` and WebKit
XPC services inside the simulator runtime; Playwright WebKit = its process tree
plus anything under `ms-playwright`. The value is ps RSS (bytes). It is not the
Windows working set the baseline measured, it excludes compressed memory (a
lower bound on macOS footprint), and Safari's count includes its helper
extensions. The attribution rule was committed before the first run and is not
narrowed after seeing results; any narrower breakdown is labelled diagnostic.

## Limits

`thresholds.json`, generated by `derive-thresholds.mjs` from
`tests/adoption_acceptance/baseline.json` and committed before any macOS run
(see git history): the adoption harness's own WebKit rows -- timing p95 <=
ceil(WebKit quiet p95 x 1.5 + 100 ms); sampled working-set maximum <=
ceil(historical long WebKit maximum x 1.25 + 128 MiB). Every row is a gate. A
test asserts the file is exactly what the derivation produces.

## What a result means

GitHub's macOS runners are virtual machines, not the user's Macs, iPhones or
iPads: no physical GPU or display, different memory and thermal behaviour, and
a simulator is not a device. The baseline is Windows Playwright WebKit measured
with a different quantity. A pass is bounded regression evidence for the engine
family; a failure is a measured exceedance to investigate, never a reason to
change a limit. Neither is a device RAM budget or certification.
